### Consumer upgrade path — real gap, no existing mechanism

`brain/core/config-migrations.mjs` only migrates `brain.config.json` schema keys (additive defaults) — it has NO mechanism to (a) `git rm --cached` a consumer's own tracked `.memory/manifest.json`, or (b) `git config --unset merge.engram-manifest.driver` in a consumer's `.git/config`. `.memory/**` is NOT in `managed-paths.mjs`'s `managed` list (it's consumer data, never copied/deleted by `brain:upgrade`). So: on upgrade, a consumer's `.gitattributes` gets overwritten (COPY strategy) to drop the `merge=engram-manifest` line, and `brain/scripts/**` drops the driver-registration code and `merge-engram-manifest.mjs` file — both harmless-dangling, since nothing will invoke the driver once the attribute line is gone. But **the consumer's own `.memory/manifest.json` stays git-tracked in their repo forever** unless the proposal adds an explicit one-time consumer-side migration step (new territory — no existing installer hook does this). This is a genuine, unaddressed gap the proposal must rule on.

### Candidate approaches

1. **Single PR, full scope** (manifest+driver+symlink+gitattributes+gitignore+REQ-3, dualWriteRecords+its tests, legacy gz+secret-scrub gz functions+collectChunkObservations rows). Pros: one coherent "artifact estate closes" story, matches tasks.md's literal text. Cons: counted-line estimate sits at the edge of the 400-line budget; couples an irreversible rollback-safety deletion (legacy gz) to a lower-risk transport cleanup (manifest/driver); if 1.2a hasn't landed yet, this PR has to carry a documented reasoning why `dualWriteRecords` is safe to delete without it. Effort: Medium.

2. **Two-slice chain**: Slice A = manifest/driver/symlink/gitattributes/gitignore/REQ-3 (the #803-adjacent, lower-risk half, confirmed unblocked by 3.2). Slice B = dualWriteRecords + its tests + legacy gz/migration-rejected.json + secret-scrub gz functions + collectChunkObservations rows (the irreversible-rollback-loss half, and the piece that must sequence after — or explicitly declare independence from — 1.2a). Pros: isolates the irreversible decision (rollback safety net) for separate review attention; keeps each PR comfortably under budget; lets 1.2a merge or be explicitly ruled out before slice B locks in the dualWriteRecords deletion. Cons: two PRs/tickets instead of one; tasks.md currently models 2.4 as one ticket. Effort: Medium, same total work, better reviewability.

### Recommendation

Slice per option 2. Slice A has no open dependency risk (3.2 is done, confirmed no writers of manifest.json remain) and should proceed first. Slice B should explicitly rule the 1.2a question in its proposal (this exploration's finding: dualWriteRecords is not needed by 1.2a's actual heal mechanism, a duplicate-row deletion inside the engram store, not an observations→records write) rather than leave it open, and must state the legacy-gz rollback-loss cost as an accepted, irreversible cost in the proposal text, not silently. Both slices should explicitly flag the consumer-upgrade gap (no mechanism to untrack a consumer's own `.memory/manifest.json` or unset their stale git config) as an open question for the proposal to rule on — it is not fixable within 2.4's own file scope.
