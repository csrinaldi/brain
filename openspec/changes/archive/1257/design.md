# Design — nonblocking-forge-reads (issue 1257)

## Technical approach

This change was split out of #1199 on 2026-10-02 by maintainer ruling. Its decisions keep the numbers they had in #1199's design (D53–D58 and D63–D67), so a reader can follow each one across both changes. D68 is new and records the seam that the split creates. #1199 keeps D50–D52 and D59–D62. Line numbers refer to `cef42973`. The requirements implemented here are R1257-1 to R1257-11 in `spec.md`.

```

ui/forge-thread.mjs    one worker thread per forge lane; the event loop never runs a spawn   (D63)
```

## Cold start today (the evidence for R11)

**Logically, the first render does not read the forge.** `listen` computes `current` at `ui/server.mjs:393`, before `poller.start()` at `:399`. That snapshot is built over the cache-only port (`:105-106`, `:194`), and an empty cache throws at once with "the first forge poll has not completed" (`forge-cache.mjs:23,54`). `/api/snapshot` (`server.mjs:339-343`) and the SSE `sync` frame (`:345-351`) serve that held `current`, so neither calls the forge.

**Physically, they do wait.** Every forge verb is a `spawnSync`: `vcs/lib/exec.mjs:6,20-21` and `runJson` at `:39-42`, reached through `ghJson` (`github.mjs:72`). Each adapter verb is an `async` function that never yields before its spawn, so it blocks the thread that calls it. That thread is the server's:

1. `poller.start()` runs inside `onListening` (`server.mjs:399`), before `resolve(api.port)` at `:400`. `runTick` → `forgeLane` evaluates `Promise.all([vcs.issueList(...), vcs.mrList(...)])` (`poller.mjs:213-216`), and both spawns run synchronously inside that expression. `listen` cannot resolve, and `main()` cannot print "listening" (`server.mjs:538,551`), until both lists have returned.
2. The review lane (`poller.mjs:228-231`) and the cold-start body lane then run. The cold-start body lane is uncapped (`:157`, about 133 `issueView` spawns) and runs inside `bodyTargets.map(async …)` (`:235-241`). Each callback spawns before its first `await`, so the spawns run back to back. The awaits between them resolve as microtasks, and the event loop never gets an I/O turn.
3. While this runs, the HTTP server answers no request, not even `GET /`. At about 1 s per `gh` call, the cold tick holds the server for roughly two minutes. Every later tick holds it for its two lists, up to 10 reviews and up to 25 bodies.
4. Even after the block ends, the graph appears only when the whole forge lane settles, because `onTick` fires in `runTick`'s `finally` (`poller.mjs:306-309`). Until then, the graph section reads "the issue list could not be read: the first forge poll has not completed" (`snapshot.mjs:365`). `failedSections` (`banners.mjs:64-69`) reports that as a failure, not as loading.

R10 removes item 2's body reads. It does not remove items 1, 3 and 4, and a full closed list run as one `gh api --paginate` spawn would block for about 13–16 s. D63 moves the spawns off the event loop, D65 states loading, and D66 shows the graph as soon as the open list lands. The first RED in `tasks.md` turns items 1 and 3 into a failing test.

## Testing strategy (strict TDD, node:test)

- No test touches the network. Forge reads come from `readOnlyPort` fakes keyed on `state` (`snapshot.test.mjs:290-333`), from poller fakes `vcs`/`closedVcs`, or from a test adapter module loaded by a real worker.
- Poller tests use `fakeScheduler` (`poller.test.mjs:28-42`). "Held" calls are promises the test resolves by hand.
- The only timing constants are tick counts, `CLOSED_SINCE_OVERLAP_MS` (asserted as an arithmetic difference between two injected `_now` values), and the `Atomics.wait` deadlock guard, which no passing run reaches.

**First RED** is the event-loop probe in `ui/server.test.mjs` (R1257-9, "An HTTP request waits on a forge read today"). It starts `main()` on a free port with `_resolveForgeSource` and `_forgeThreadResolve` both pointing at one test adapter, `ui/test-support/blocking-forge-adapter.mjs` (beside the existing `git-remote-fixture.mjs`). Its `issueList` signals "blocked" and then calls `Atomics.wait` on a shared `Int32Array`. A helper worker waits for "blocked", requests `GET /`, and on the response stores and notifies the release slot. Today `main()` ignores `_forgeThreadResolve` and runs the adapter on the server's thread, so the request cannot be answered, the wait times out, and the test fails on "timed-out". Once `main()` runs the adapter in a forge thread, the same test passes unchanged.

## Risks

- **The closed-list cost is estimated, not measured directly** (D55, D67). Apply measures it with `time gh api --paginate 'repos/csrinaldi/brain/issues?state=closed&per_page=100' --jq length`. On its own thread, a higher number delays only the closed data.
- **The delta anchor is local time** (D56). A host clock more than 10 minutes ahead of the forge could miss a closure in a delta. The hourly full re-list bounds that miss to one hour.
- **A just-closed issue is briefly in neither list**, for about one interval. It is never shown with a wrong state.
- **Shutdown may wait for one in-flight spawn.** `Worker.terminate()` cannot interrupt a `spawnSync` in progress. `main()`'s signal path exits the process anyway (`server.mjs:562`).
- **The probe binds a port it picked free a moment earlier.** Another process could take it in between; the test then fails with `EADDRINUSE`, never with a false pass.
- **A stateless row no longer blocks** (D58). Production payloads carry a state; test fakes must too.
- **`vcs-contract.md` lags** until the maintainer promotes the draft.
- **The design runs past the skill's 800 words**, because it carries the cold-start evidence and eleven decisions moved intact for traceability.

## Follow-up #1256

**Title:** feat(ui): persist the forge cache across `brain:ui` restarts, so a cold start paints forge data at once

**Brief:** Since #1257, no view's first render waits on a forge read. The first paint comes from the local tree plus the cached forge data, and the open and closed lanes, each on its own worker thread, fill in while `forgeLoad` says what is still loading. The cache (`brain/scripts/ui/forge-cache.mjs`) lives only in process memory, so every restart begins with every forge-backed view pending: about 2.5 s for the open list, and about 13–16 s before the full closed list lands. The closed lane must also re-read that full list before it can return to deltas. Persist the cache's lists (open issues, closed issues, the MR list and reviews), with their `forgeLoad` timestamps and the closed lane's delta anchor, under a gitignored path. Load them before `listen` computes the first snapshot, and resume the closed lane with a delta from the persisted anchor. Report restored lanes in a way the #1251 resolver can tell apart from a live `complete`, for example a `restoredAt` field, or a `stale` state until the first live landing. Out of scope: the `brain:snapshot` CLI, which stays cold and deterministic. Open questions: the file's location and format, invalidation when the provider, project or identity changes, and a size bound.
