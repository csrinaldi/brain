## Exploration: issue #920 — shipLane() skips PR reconciliation on a no-new-commits retry (audit M1)

### Current State (base: feat/issue-920-ship-reconcile @ main b61b5a95)

`shipLane()` in `brain/scripts/memory/lane/ship.mjs` is `collect → survey → [early return] → push → buildTitleAndBody → findOrCreatePr → mrAutoMerge`:

1. `collectLane()` (collect.mjs:199-350) — mints/advances the local lane ref via CAS `update-ref`. Returns `commit` (new commit sha or `null` if the tree diff vs. parent was empty — collect.mjs:289-293) and `collected` (count of genuinely new paths, collect.mjs:305-310).
2. `surveyRef()` (ship.mjs:47-66) — `git rev-parse --verify <ref>`; if absent → `{ahead:0, behind:0, remoteRefPresent:null}` (ship.mjs:49-51, nothing ever collected here). Else fetches `origin/<branch>`; absent remote ref → real `ahead` via `rev-list --count <ref>`, `behind:0`, `remoteRefPresent:false` (a create). Fetch failure (any other reason) → `{ahead:1, behind:null, remoteRefPresent:null}`, a sentinel that never masks "nothing to do" (ship.mjs:55-60). Success → real ahead/behind via two `rev-list --count` calls, `remoteRefPresent:true` (ship.mjs:63-65).
3. **Early return** — ship.mjs:243-253: `if (commit === null && ahead === 0) return {...pushed:false, pr:null, autoMerge:null}`. This is BEFORE push, `buildTitleAndBody()`, `findOrCreatePr()` (ship.mjs:281), and `mrAutoMerge` (ship.mjs:304).
4. `behind > 0` pre-check refuses before any network call (ship.mjs:259-263); an *unknown* divergence (`behind:null`) still reaches the real push, which is authoritative (A3).
5. `git push --no-verify origin <ref>:<ref>` (ship.mjs:265); non-fast-forward stderr → `diverged`, other non-zero → `pushFailed`.
6. `buildTitleAndBody()` (ship.mjs:91-110) — host/date re-parsed from the BRANCH (never raw params, since `slugifyHost()` in `lane/plan.mjs` can rewrite host), `Records: n` from a three-dot diff `origin/main...<ref>`, never from `collected` (#887's own C1 lesson: `collected` is this-run-only). A non-zero diff exit reports the count as `unknown`, never `0`.
7. `findOrCreatePr()` (ship.mjs:137-174) — `vcs.mrList({project, state:'open'})` (the ONE port verb that throws, tagged `prLookupFailed`); find by `headBranch`; else `vcs.mrCreate(...)`, tagged `prCreateFailed` if no url; PR number is parsed from the URL (`parsePrNumber`, ship.mjs:121-128) with a one-shot `mrList` re-scan fallback if unparseable — both failing leaves `pr.number:null`, non-fatal (self-heals next run via `mrList`'s idempotent find).
8. `mrAutoMerge` (ship.mjs:302-307) — only reached if `pr.number !== null`; wrapped in try/catch so a throw degrades to `{enabled:false, reason}`, never fatal (E2, the push+PR already landed durably by this point).

### Why the early return exists (must not regress)

Block comment ship.mjs:226-242 (A1's "REFINED predicate") + cold-1 (PR #902 review): before this fix, `buildTitleAndBody()` ran unconditionally right after `collect()`. For a ref that NEVER existed (first run, nothing to ship — `commit:null`, `surveyRef`'s `rev-parse` fails → `ahead:0`), the three-dot diff against a ref that has no local existence fails, and that failure was reported as "origin/main could not be fetched" — conflating "the local ref never existed" with "the remote base is unreachable". Test `ship.test.mjs:119-143` ("cold-1") pins this: no `diff` call, `title:null`/`body:null` (not a fabricated title), for the ref-never-existed case.

Invariants any fix MUST preserve:
- A ref that never existed locally must never be diffed (no misleading "could not be fetched" report) — `ship.test.mjs:119-143`.
- `title`/`body` stay `null` (not absent) whenever there is genuinely nothing to title (C3, ship.mjs:244-248).
- `buildTitleAndBody()` stays deferred until AFTER it's known a push-or-reconcile will actually happen — never called on a pure no-op.
- The already-fully-shipped case (remote == local, PR merged/closed, nothing pending) must still be a true no-op: zero push/mrList/mrCreate/mrAutoMerge calls when there is truly nothing to reconcile. **`ship.test.mjs:93-117` currently pins commit:null+ahead:0 as an UNCONDITIONAL no-op — this exact test will need to split into "no ref ever existed" (still no-op) vs. "ref exists, ahead:0, but PR unreconciled" (must now call findOrCreatePr) once the fix lands.**
- `behind > 0` must still refuse before touching the network (pre-check, ship.mjs:259-263).
- `mrList` throwing must still fail the run closed (`prLookupFailed`) rather than risk a blind `mrCreate` duplicate.

### The gap precisely

`ahead === 0` only tells you "the local ref and `origin/<branch>` point at the same commit" (or, if `remoteRefPresent:null`/local ref never existed, a degraded signal). It says NOTHING about whether a PR was ever opened for that branch, or whether it reached `main`. `commit === null` only tells you "this run's collector found nothing new to add." Both conditions can be true even when:
- the push succeeded but `findOrCreatePr()` threw (mrList outage) or `mrCreate` failed silently in a way the caller didn't observe,
- the push succeeded, the PR was created, but `mrAutoMerge` arming failed and was never retried,
- the PR was merged (squash) and its remote branch was auto-deleted — `ahead` would then read via `remoteRefPresent:false` path (a "create") on the NEXT collect cycle for a NEW commit, but a retry with zero new commits and a deleted remote branch is currently unreachable analysis (ahead:0 only holds while the branch still exists at the same sha as local).

The audit's own reproduction (M1, quoted in the issue) demonstrates the mrList-outage variant with an in-process seam; the mrAutoMerge-arming variant and the merged/closed/branch-deleted variants are inferred from the same code path, not yet reproduced.

Rows 6-11 are exactly the audit's open questions 1 and 2 (memory-audit-handoff-2026-09-10.md lines 223-224) — they are NOT settled by this exploration; they are what the proposal must rule on.

### "Delivered" vs "to deliver" — what a reconciliation read needs

- `ahead === 0` (local ref == `origin/<branch>`) is NECESSARY but not SUFFICIENT for "delivered" — it only proves nothing is queued to push, not that the PR reached `main`.
- `mrList({project, state:'open'})`'s returned shape is `{number, title, headBranch}` ONLY (pinned by `vcs.contract.test.mjs:391-403`, both providers normalize to exactly this — no `url`, no merge/close state). **There is no existing helper or port verb that tells the caller "this branch's PR is merged" vs. "closed unmerged" vs. "never existed."** Querying `state:'closed'` or `state:'all'` would return matches, but the normalized shape still carries no merged-vs-closed-unmerged distinction — GitHub's REST `pulls` list exposes `merged_at` but `mrList()` (github.mjs:457-460) does not surface it, and the contract test pins the narrower shape.
- The only other read available is `remoteRefPresent`/whether the remote branch still exists (from `surveyRef`'s fetch), which conflates "merged and auto-deleted" with "never pushed" and with "force-deleted for other reasons."
- Net: a real reconciliation ("is this PR merged?") needs either (a) a new/widened port verb (e.g. `mrList` gaining a `merged`/`state` value beyond open, or a `mrGet(number)` returning merge state), or (b) inferring "merged" indirectly from `git merge-base --is-ancestor <local-commit> origin/main` after a fetch — i.e., asking git directly whether the lane commit already landed on `main`, which sidesteps the port's shape gap entirely and doesn't require a new port verb. Both are legitimate directions; this is the central design fork for the proposal.

### Test surface

- `ship.test.mjs:93-117` — **pins the exact buggy predicate** as correct behavior today (`commit:null && ahead:0` → zero push/list/create/arm calls). This test's fixture (`fakeCollect({commit:null})` + `surveyOkRules` overridden to `ahead:'0', behind:'0'`) does NOT distinguish "ref never existed" from "ref exists, remote matches, but PR is unreconciled" — the fake `git` rules return `rev-parse` success (`ok('deadbeef')`), i.e., it currently exercises the "ref exists" sub-case, which is the exact one issue #920 says is wrong. This test WILL need to change or split.
- `ship.test.mjs:119-143` ("cold-1") — pins the ref-never-existed sub-case (`rev-parse` fails) as a true no-op; this one must NOT change.
- `ship.test.mjs:145-161` ("A1 recovery case") — pins `commit:null, ahead:1` (a prior push failed, local ref ahead) as already correctly retrying push+PR+arm; unaffected.
- `fakeVcs()` (ship.test.mjs:59-68) and `recordingVcs()` (ship.integration.test.mjs:66-87) can already express "PR exists, found by headBranch", "mrCreate succeeds/fails", "mrAutoMerge succeeds/throws/refuses" — sufficient to express reconciliation-retry scenarios in the unit suite.
- Neither fake currently expresses "PR merged" or "PR closed" as a distinct `mrList` entry shape (since the contract shape has no such field) — any test asserting "must not re-create a PR for an already-merged branch" will need either a fixture convention (e.g. absence from the open-list) or a new field, matching whichever port-shape decision the proposal makes.
- **Integration precedent for a local bare remote already exists**: `brain/scripts/memory/lane/ship.integration.test.mjs` (`buildFixtureRepo()`, lines 47-60) — `git init --bare` as `origin`, a `main` checkout pushed to it, `testTmp()` from `../../lib/test-tmp.mjs`, mirroring `collect.integration.test.mjs`'s own fixture. It already has a "killed push...recovers on re-run" test (lines 149-165) that is the closest existing analog to what M1's fix needs; a new test for "successful push, PR lookup fails, retry with no new commits reconciles" should follow this exact pattern (real git + bare origin + `recordingVcs()`, injecting an `mrList` that throws on the first call only). NEVER against the real GitHub/GitLab providers or a real remote — `BRAIN_VCS_TEST_MODULE`/`fake-vcs-port.mjs` is the CLI-level seam (cli.mjs:399-425); the integration test uses its own in-process fake port instead, which is stricter and preferred for this repro.
- `ship.test.mjs` also has a `# ── Requirement: mrList throwing is the one fatal port failure` section (line 495) — any reconciliation retry path must keep `mrList` throwing fatal-and-closed, not swallow it.

### Blast radius (callers of shipLane)

1. **`brain/scripts/memory/session-end-ship.mjs`** (`shipOnSessionEnd`) — spawns `cli.mjs ship --json` DETACHED, discards the child's exit code entirely (header comment ship.mjs:32-33... actually session-end-ship.mjs:29-33: "the child's own exit code is never read"). It only cares that spawning itself didn't throw. A reconciliation fix changes NOTHING here structurally — this caller never inspects the outcome shape at all, only whether the subprocess launched.
2. **`brain/scripts/memory/day-start-sweep.mjs`** (`runLaneSweep`/`laneSweepLine`) — runs `ship --json` SYNCHRONOUSLY with a 60s timeout, parses the single JSON stdout line, and `laneSweepLine()` (day-start-sweep.mjs:76-105) renders exactly three outcomes: `skip` (lane disabled), `warn` (non-zero exit or unparseable JSON), or `ok` — and the `ok` branch further distinguishes `outcome.pushed` truthy ("shipped", using `outcome.ref`/`outcome.pr?.number`) vs. falsy ("nothing"). **This is the field a reconciliation fix must account for**: today `pushed:false` always co-occurs with `pr:null` in the no-op case, so "nothing" is accurate. Once a fix makes commit:null+ahead:0 sometimes trigger `findOrCreatePr`/`mrAutoMerge` WITHOUT a push, `outcome.pushed` will stay `false` even though real reconciliation work happened (a PR got created/found, or armed) — `laneSweepLine()`'s `nothing` branch would then under-report a real reconciliation as "nothing to ship". The outcome shape likely needs a new boolean (e.g. `reconciled`) or `laneSweepLine()` needs to also branch on `outcome.pr !== null`/`outcome.autoMerge` to stay accurate. This is a concrete downstream contract change, not just an internal ship.mjs detail.
3. **`memory/cli.mjs`'s `ship` op** (cli.mjs:446-533) — reads the FULL outcome shape: `result.pushed`, `result.pr`, `result.pr.url === null && result.pr.number !== null` (existing-PR message), `result.autoMerge?.enabled`, `result.identityBound`, plus `shipOutcomeKey()` (cli.mjs:539-545) which maps the whole shape to one message key (`dryRun`/`prNumberUnknown`/`nothing`/`autoMergeRefused`/`done`). `shipOutcomeKey()`'s `nothing` branch (`pushed === false && pr === null`) will also go stale for reconciliation-without-push (pr would be non-null with pushed:false) — it would currently fall through to `done`, which is misleading text ("done" implies delivery when only reconciliation, not push, happened) unless a new key is added. `--dry-run`/`--json` both pass the full outcome through unchanged; `--json` just serializes whatever shape `shipLane` returns, so it's automatically forward-compatible with new fields, but `--dry-run`'s branch (ship.mjs:215-222, returns before `surveyRef`) is UNAFFECTED by this fix — the early-return bug lives entirely past the `dryRun` branch.
4. **`dryRun` and the collector**: ship.mjs:211-214 notes `collect` still runs its own best-effort `git fetch origin main` under `--dry-run` — this DOES matter for a reconciliation fix if the fix wants `--dry-run` to also report "reconciliation would happen here" (currently `--dry-run` never reaches `surveyRef`/`findOrCreatePr` at all, so it cannot preview a reconciliation-only run today). Whether `--dry-run` should learn to preview reconciliation is an open question for the proposal, not a given.

### Approaches (high-level, not a recommendation — for the proposal to weigh)

1. **Split the predicate**: replace `commit === null && ahead === 0` with two independent questions — "anything to push?" (`commit !== null || ahead > 0`) and "anything to reconcile?" (local ref exists AND a PR is not yet found+merged+armed). Only skip `findOrCreatePr`/`mrAutoMerge` when BOTH are false, i.e. drop the old return's exclusive-or shape into an AND of two independent no-op checks — one skips push, the other skips reconcile, and only the intersection is a true no-op.
   - Pros: smallest structural change, keeps existing invariants text mostly intact, cheapest to review.
   - Cons: still needs an answer to "how do I know a PR is already merged" (the port-shape gap above) or it will spuriously re-create/re-list on every fully-delivered day forever (an extra `mrList` call every run is functionally-safe-but-wasteful; re-`mrCreate`-ing would NOT be safe and must be guarded).
   - Effort: Medium.

2. **Positive "merged" signal via git, not the VCS port**: after a successful (or already-matching) push, run `git merge-base --is-ancestor <local-commit-or-ref-tip> origin/main` (after a `fetch origin main`) as the reconciliation-complete check, bypassing `mrList`'s shape gap entirely. Only call `findOrCreatePr`/`mrAutoMerge` when the lane tip is NOT yet an ancestor of `origin/main`.
   - Pros: sidesteps the port contract gap (no provider change needed), directly answers "did this land on main" which is the actual goal (not "is there an open PR"), naturally handles the squash-merge+branch-deleted case (row 7) correctly (ancestor check says "yes, delivered", no re-push, no re-PR).
   - Cons: adds another git round-trip every run; needs to fetch `origin/main` (already done in `collectLane` step 1, so may be cheap/duplicate); does NOT by itself resolve the "PR exists but is closed unmerged, records still pending" case (row 8) — still needs `mrList` for that.
   - Effort: Medium-High (new seam, new tests, touches the core predicate + the ancestor read).

3. **Widen the VCS port** (`mrList` gains real state/merged info, or a new `mrGet(number)` verb): fixes the shape gap at the source, benefits every future caller that needs merge-state, but is the highest-blast-radius option — touches `vcs/providers/github.mjs`, `gitlab.mjs`, the contract test (`vcs.contract.test.mjs`), the fake port fixture, and is arguably out of scope for a bug-fix-sized issue (#920 vs. a port-design ticket).
   - Pros: most correct long-term; removes the git-merge-base workaround.
   - Cons: largest surface, crosses into provider/port design (likely needs its own design doc / possibly a separate ticket), risks scope creep on what the issue frames as a bug fix.
   - Effort: High.

4. **Do nothing about rows 6-11, fix ONLY the reproduced mrList-outage variant** (narrowest read of the issue's acceptance criteria: "retries with no new commits but unreconciled remotes invoke findOrCreatePr/mrAutoMerge" could be satisfied by tracking "did the last successful run's PR/arm step complete" via a NEW local marker (e.g. a note in the commit message, a sibling ref, or a returned/cached flag) rather than re-deriving merge state from the port at all).
   - Pros: smallest, most surgical; doesn't touch the VCS port; directly targets the reproduced defect.
   - Cons: doesn't address the squash-merge/branch-deleted/date-change open questions the issue's acceptance criteria explicitly calls out ("proper handling of records added post-squash-merge and date transitions") — likely insufficient against the issue's own acceptance criteria.
   - Effort: Low-Medium.

None of these is a recommendation; the proposal phase should weigh them against the acceptance criteria and the open questions below, and should read the issue's explicit callout that "Integration testing with local bare repositories using the fake VCS fixture" is a stated acceptance criterion — approach 2's ancestor check is the one most naturally verified that way (`ship.integration.test.mjs`'s existing fixture already has everything needed: a real bare origin, `git merge-base`, no port change).

### Risks

- The state-space table's rows 6-11 are NOT settled — any proposal that ships without an explicit ruling on "squash-merge + branch auto-deleted" and "date change with prior day pending" risks introducing a NEW defect (e.g. re-opening a PR for already-merged, already-deleted-branch records) while fixing M1's narrower reproduced case.
- `ship.test.mjs:93-117` is a load-bearing test that currently encodes the bug as correct behavior — it must be consciously split/rewritten, not just weakened, or the fix will regress silently under CI.
- `day-start-sweep.mjs`'s `laneSweepLine()` and `cli.mjs`'s `shipOutcomeKey()` both currently assume `pushed` is the only signal of "something happened" — a reconciliation-without-push path will misreport as "nothing" unless both are updated in the same change.
- The VCS port's `mrList` shape (`{number, title, headBranch}` only) cannot today distinguish "merged" from "closed unmerged" from "never existed" — any fix that leans on `mrList` for merge-state (rather than the git-ancestor read) needs either a port change (high blast radius, likely its own ticket per #890's sequencing precedent in the audit) or an accepted limitation.
- `--dry-run` currently never reaches the reconciliation path at all (returns at ship.mjs:215-222, before `surveyRef`) — if the proposal wants dry-run to preview a reconciliation-only run, that is new scope, not a side effect of moving the predicate.
- No ticket-specific test for the mrAutoMerge-arming-failed-then-retried variant of M1 exists yet (only the mrList-outage variant was reproduced in the audit and is pinned nowhere in the current suite).

### Ready for Proposal
Yes — with the explicit caveat that the proposal phase must first RULE on the open questions (rows 6-11 of the state-space table, corresponding to the audit's open questions 1 and 2) before choosing among the four approaches, since the choice of "how do we know something is reconciled" (git-ancestor vs. port-shape vs. local marker) determines which rows are even answerable without a VCS port change.
